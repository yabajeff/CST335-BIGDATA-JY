the folder layout is mimicking how real lakehouses will store their data. The data files will sit inside of plain folders under the `lakehouse/engagement/`, and then split by the `year=2024/month=MM/`. This also ends up being the same Hive-style naming system that popular platforms use such as: Delta Lake, Iceberg, and Spark. Because the different partition values are inside of the folder names, a query engine can be made to skip the whole folders that don't match with a filter. Query 1 is only reading the September folder, and then Query 2 is filtering on `month = 10` so that the other months can be skipped with efficiency. Without the metadata, this same folder of the CSVs could turn into a data swamp and we would not want that. In turn, this might create problems for files with different columns for each or those with no record on what the types should be, or even no way to know which files end up belonging to the table. The YAML metadata files is helping to prevent this by first defining the schema, then the required columns, allowed values, partition keys, the list of files in the table, and then finally the current version at the end. Anyone querying or using the lakehouse can read also the metadata and then also know what to expect.

the ACID transactions are not integrated here, but they are an important essential for a real lakehouse. If two jobs were to write the table at the same time, or if a write were to fail halfway, the readers could see some partial or mismatched data as a result. Different formats like the ones used at Delta Lake, Iceberg, and Hudi end up solving this problem with a transaction log. A new file will only become a part of the table when the log itself is updated within one atomic step, so that the readers always end up seeing a complete version as a result. The versioned metadata files are a more simple version of this concept I believe, since the version 2 ends up listing the November file and version 1 doesn't. Open table formats do matter because of the reliability they bring to the table, on top of cheap and open file storage as well as many different reliable engines like Spark, Trino, DuckDB, Snowflake can read the same tables without any problems.

This does end up being a little more unique than a traditional warehouse would be in a few different ways. A warehouse typically stores its data in its own internal format, this does require the schema up front (schema-on-write), and then will handle the transactions and storage together inside of one singular system. A lakehouse will keep its data as open files inside of object storage, as well as separating the storage from compute (here DuckDB is just the compute layer reading each of the files), and then also will support the schema-on-read and schema evolution, while also still adding some warehouse-style features like the schemas, enforcement rules, and the transactions through each of the metadata layers.
