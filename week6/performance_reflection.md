DuckDB is storing and processing the data by columns instead of by rows. A majority of the OLAP queries are only touching two or three of the columns, such as the `item_key` and `loan_count`, so this means that DuckDB only has to read those columns instead of every field within the table. It also processes each of the values within batches (this is also called vectorized execution), which then makes the aggregations like SUM, COUNT, and AVG much faster. Currently, with only 36 rows the speed difference is not that significant, but the same design would see different results with millions of loan records.
The star schema keeps the joins simple. Every of the queries joins the fact table directly through the one or two dimensions it needs, using different integer surrogate keys, and there are also no chains of joins between each dimension tables. An example would be like, loans by semester and campus is just `fact_loans` joined to `dim_date` and then `dim_campus`. Filtering also then reduces the amount of data scanned. Inside the slice query, `WHERE semester = 'Fall 2025'` is limiting the work to one single semester. If the fact table were to be larger, it could be partitioned by each year or semester (for example, one Parquet file per one semester) so DuckDB could skip the partitions that don't match the filter.
Any materialized views, or pre-aggregated summary tables, could end up speeding the dashboard workloads in the long run. A dashboard showing the monthly loans by category are ran by the same aggregation every single time it refreshes. Storing this result inside a summary table would let the dashboard read a some pre-computed rows instead of taking more time and re-scanning and re-aggregating the fact table over again.
